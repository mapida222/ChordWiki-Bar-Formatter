# 変換後編集のデータフロー調査

## 現状

変換前、行修正、変換後は、同じ行番号を対応キーとして管理している。
変換後の直接編集行は `manualOutputLines` の行番号集合、行修正は改行区切りの配列、自動値と白玉数も同じ添字の配列で保持する。

純粋な改行追加・削除だけで文字列本体が同じ場合は、`synchronizeLineBreakLayout` がコード／白玉スロット順に行修正を再配分する。
また、一般の行増減では `alignLineIndices` が前後の行を対応づけ、復元可能な拍コードだけを推論する。

## 崩れる条件と原因

改行と同時に振り仮名、コード、拍記号なども変更すると、「改行位置だけが変わった」と証明できない。
この場合は行文字列の類似対応と拍コードの逆推論へ移るが、次の情報は一意に復元できない。

- 新しい行がどの変換前行から派生したか
- 直接編集したコードが原文変更か表示上書きか
- 自動追加した拍記号とユーザーが残したい拍記号の境界
- 分割後のどの行が従来の行修正／固定状態を所有するか

根本原因は、編集対象の同一性が安定したIDではなく可変な行番号に依存していることにある。

## 選択肢

### 1. 変換後編集を変換前へ明示適用

コードと歌詞だけなら分かりやすいが、自動追加記号を原文へ戻すかを判断できない。
「適用」操作に差分確認と競合解決を用意しない限り、原文を意図せず汚す危険がある。

### 2. 常に変換前から再生成

モデルは最も単純になるが、変換後の手動調整が失われる。
現在の利用方法とは互換性がない。

### 3. 変換結果と手動上書きを別レイヤー化

推奨案。
変換前の各音楽行へ安定IDを付け、自動生成結果とは別に「文字差分」「改行レイアウト」「固定拍」の上書きを保存する。
再変換時は安定IDと音楽トークン境界で上書きを再適用し、競合した箇所だけユーザーへ選択を求める。

## 今回の判断

別レイヤー化は変換・履歴・localStorage・リアルタイム編集の保存形式をまたぐ変更になるため、今回は実装しない。
既存の純粋な改行再配分は維持し、変換後枠には「改行・振り仮名・コード修正は変換前で行う」旨を短く表示する。
詳細な最終調整は、行修正と再変換から独立したリアルタイム編集ページを使用する。
